# 자주 묻는 질문

### Q. 1차 점수가 2차 점수에 합산되나요?

아닙니다. 1차 점수는 2차 참가자를 뽑는 데만 쓰이고 2차 점수(Q·CII)에는 더해지지 않습니다.
2차는 2차 결과만으로 새로 채점합니다.

### Q. self-score가 공식점수인가요?

아닙니다. self-score는 공식점수가 아니라 **스스로 해 보는 준비도 점검**입니다. 공개 연습(rehearsal)에서
각 항목에 자신이 0–4 anchor를 매기고 공개된 lookup 표에 넣어 예상 Q를 계산해 보는 것뿐입니다.

실제 채점에서는 앱이 스스로 매긴 점수나 anchor를 전혀 읽지 않습니다. 대신 Dacon 자동평가기가 사전에
동결된 숨은 판정기준과 hidden Probe 실행 결과를 대조해 anchor와 Q를 직접 만듭니다.

### Q. APK를 올릴 때마다 Dacon이 AUTO-CHECK 점수를 알려 주나요?

아닙니다. 개발 중에는 응시자가 공개 연습도구 또는 앱의 public UI로 공개 input을 직접 반복 실행하고,
self-score로 준비도를 확인합니다. Dacon은 이때 hidden input을 실행하거나 official 점수를 회신하지
않습니다.

Dacon은 최종 제출 마감 뒤, 마감 receipt가 가리키는 최종 접수본을 CODE/SEC 검사하고 적격 APK
전원에 AUTO-CHECK를 실행합니다. 마감 전 재업로드 허용여부는 Dacon 페이지 규칙을 따르지만,
허용되더라도 각 업로드를 반복 채점해 개선기회를 제공하는 방식은 아닙니다. 운영환경 장애가 확인된
재실행만 incident 절차에 따라 같은 동결 APK로 수행합니다.

### Q. 점수표를 공개하면 hidden이 유출되지 않나요?

공개하는 것과 감추는 것은 다릅니다. **무엇을 확인하고, 어떤 0–4 기준(anchor)으로, 어떻게 점수를
계산하는지**는 모두에게 공개합니다. 반면 **실제 시험에 쓰는 값·순서·구성, 각 항목의 정답(기대 상태와
금지 결과), 합격·선정 커트라인**은 공개하지 않습니다.

즉 “채점 기준을 공개하는 것”과 “시험 정답을 공개하는 것”은 다릅니다. 기준을 알아도 hidden 값과 정답까지
알 수는 없습니다.

### Q. 공통 JSON import나 자동화 API를 만들어야 하나요?

예. AUTO-CHECK이 최종 운영방식으로 채택됐으므로 모든 참가자가 자기 APK 안에 ① 표준
점검 입구(Probe Mode)와 ② 각 CORE·operation이 내 앱의 어디에 대응하는지 적은 연결표
(`MISSION_ADAPTER.json`)를 넣어야 합니다.

같은 production core에 연결된 두 입구로 시험합니다. **공개 연습용 세트**(public pack)는 참가자가
공개 연습도구 또는 앱의 public UI로 직접 실행하고, **실제 채점용 세트**(official pack)는 최종 제출
마감 뒤 Dacon이 공식 Runner의 보호된 연결부(protected component)를 통해 실행합니다. 별도의
공개 연습 전용 Runner APK가 있는 것이 아니라, 공개 연습도구도 Kit에 포함된 같은 공식 Runner APK를
공개 입력으로 구동할 수 있습니다.

### Q. SHA-256·release ID·runtime JSON을 제가 만들어야 하나요?

아닙니다. Dacon이 `MISSION_LOCK.json`을 주고, 공개 연습도구가 공개 input 실행파일을 준비하며,
공식 Runner가 공개 실행의 result를 내보냅니다. 참가자는 실제 앱 기능을 설명하는
`MISSION_ADAPTER.json`과 증거 파일만 준비한 뒤
`FINALIZE_SAMPLE_EXPORT.py`를 실행합니다. 도구가 APK·SOURCE·증거 파일을 읽어 SHA-256, release ID,
runtime identity와 파일목록을 자동으로 만들고 검사합니다. 예시 JSON의 값을 복사하거나 임의의
기술 식별값을 만들어 채울 필요가 없습니다.

### Q. 앱이 official hidden input 전체를 볼 수 있나요?

아닙니다. 앱은 그 실행에 필요한 합성 입력(role·operation)만, 한 번 쓰고 마는 형태로 받습니다. 무엇이
정답인지(oracle·기대 관계), 점수·anchor·Q, 합격 커트라인(cut) 같은 **채점 정보는 앱에 주지 않고
자동 채점환경에만** 둡니다.

입력 파일과 token은 공식 Runner가 관리하고, 앱의 보호된 연결부(protected component)는 허가된 공식
Runner의 호출만 받아들입니다. 그래서 앱이 hidden 입력 전체나 정답을 미리 볼 수 없습니다.

### Q. 앱이 스스로 매긴 점수(anchor·Q)를 결과 파일에 넣어도 되나요?

안 됩니다. 결과 파일(`PROBE_RESULT.json`)에는 **관찰된 사실만** 담습니다 — 상태(state)·판단(decision)·
행동(action)·영수증(receipt)·증거(evidence).

여기에 스스로 매긴 점수나 정답 판정 — `PASS/FAIL`, 정답 여부, 0–4 anchor, Q1–Q6, Q/80, 합격
커트라인(cut) 추정값 — 을 넣으면 규칙 위반입니다. 점수는 앱이 아니라 Dacon 자동평가기와 공개 lookup이
계산합니다.

### Q. 왜 모든 후보를 사람 Judge가 직접 실행해 보지 않나요?

기술검사를 통과한 후보는 **모두** Dacon Runner의 AUTO-CHECK(전원 자동 기본검증)을 받습니다. 그중
사람이 직접 보는 SELECTED-REVIEW(선별 수동 검증)는 세 부류에만 적용합니다: ① Q 총점과 모든 프로파일
기준을 함께 넘긴 상위권, ② gate에서 위험 신호가 있는 후보, ③ 점수와 무관하게 결과를 열기 전에 미리
뽑아 둔 표본. 이 표본에서 기계 결과와 사람 판정이 어긋나면(mismatch), 미리 정한 규칙에 따라 같은
점수대의 검증 범위를 넓힙니다.

즉 사람이 모든 후보를 처음부터 일일이 실행해 보는 것이 기본이 아니라, **전원 자동 검증 + 필요한
후보만 사람 검증**이 기본 흐름입니다.

### Q. Q1–Q6 점수는 누가 정하나요?

사람도 운영자도 Q 숫자를 직접 넣지 않습니다. 기계가 계산합니다.

- **AUTO-CHECK:** Dacon 자동 평가 batch 도구가 사전에 동결된 숨은 판정기준과 결과를 대조해 CORE별 0–4
  anchor를 만들고, 그 anchor를 공개 lookup 표에 넣어 Q를 계산합니다.
- **SELECTED-REVIEW:** 사람 Judge는 관찰한 사실·정답 판정·증거·gate만 기록할 뿐, Q 숫자를 직접
  입력하지 않습니다. 운영자도 계산식을 고치거나 임의로 점수를 더할 수 없습니다.

### Q. SELECTED-REVIEW는 AUTO-CHECK과 같은 실행을 보나요?

결과를 열기 전에 미리 정해 둔 두 방식 중 하나를 씁니다.

- **방식 A — 같은 증거를 다시 봄:** AUTO-CHECK이 남긴 그 기록을 사람 Judge가 다시 확인합니다. 같은
  실행을 보는 것이므로 다섯 가지 식별값(run·instance·token 기록·Probe 결과·증거 묶음)이 AUTO-CHECK과
  **모두 같습니다**.
- **방식 B — 새로 한 번 더 실행:** 값·순서가 다른 새 실행을 사람이 실제로 돌려 봅니다. 새 실행이라 그
  다섯 식별값은 AUTO-CHECK과 **모두 다르고**, 대신 두 Judge(J1·J2)가 **같은 하나의 새 실행**을 함께 보고
  같은 제품·동등한 시험임을 배정·동등성·release·mapping 정보로 묶어 확인합니다.

어느 방식이든 이 묶음이 서로 맞지 않거나 실제 제품 코드로 돌지 않았으면(production parity 실패), 점수를
매기지 않고 incident/HOLD 처리한 뒤 새로 배정해 다시 실행합니다.

### Q. 과거를 전부 저장하면 “선택적 기억”이 되나요?

아닙니다. 지금의 목표·사용자·대상·권한에 **필요한 근거만 골라 쓰고**, 무관한 과거 정보(distractor)가
결과를 바꾸지 않아야 합니다. 정정·철회·삭제된 정보가 앱을 껐다 켠 뒤 다시 쓰이면 실패입니다.

### Q. model(AI 모델)을 꼭 써야 하나요?

아닙니다. model 없이 규칙 기반(deterministic) 경로만으로 만들어도 됩니다. 다만 실제로 쓰지 않은 model을
썼다고 표시하면 안 됩니다. model 사용 여부와 호출수는 Starter AAR와 제출 생성 도구가 runtime
identity에 기록하므로 참가자가 별도 model 지문이나 `NOT_USED` 값을 입력하지 않습니다.

### Q. 실제 센서·다른 앱·결제를 연결해야 하나요?

아닙니다. 합성(가상) 상황과 앱 안의 미리보기·초안·상태변화로 재현합니다. 실제로 밖에 영향을 주는
동작(실제 결제·발송 등)이나 일반 APK 권한을 벗어난 제어를 해서는 안 됩니다.

### Q. comparison(비교모드)은 언제 실행하나요?

모든 참가자가 자기 APK에 넣어 두지만, AUTO-CHECK(전원 자동 기본검증)에서는 실행하지 않습니다. 확정된
Q 점수와 미리 동결한 pool 규칙으로 뽑힌 deep 후보에게만 실행합니다. Dacon OPS가 같은 조건의
full/claim-off를 실행해 원본을 남기고, 응시자는 실제 artifact를 설명·진단하며, Judge J1/J2는
짝 증거와 기술소유권·CII를 독립적으로 확인합니다.

### Q. deep 대상(pool)에 못 든 후보는 CII가 0점인가요?

아닙니다. 0점이 아니라 “평가하지 않음(`not_evaluated_not_in_pool`)”으로 기록합니다. 평가하지 않은
CII를 Q/80에 더해 가짜 /100 점수를 만들지 않으며, CII를 검증한 후보와 섞어 전체 ordinal 순위를
만들지도 않습니다. Pool은 한 번만 고정인원을 뽑는 방식이 아니라, 동결 규칙으로 추가 후보가 없을
때까지 자동 반복선정하며 인원 cap을 두지 않습니다.

### Q. 최종점수와 동점은 어떻게 정하나요?

Pool에서 `FINAL_Q`와 `FINAL_CII`가 모두 확정된 후보의 최종점수는 `Q/80 + CII/20`, 최대
100점입니다. 순위는 최종점수 → CII → Q → C3 순서로 비교하고 네 값이 모두 같으면 공동순위입니다.
기본 수상인원은 3명이지만 3위 수상경계에서 완전히 동점이면 해당 동점자를 모두 수상대상에
포함합니다. 정확한 발표시각과 이의제기 기간·경로는 Dacon 대회 페이지를 따릅니다.

### Q. gate는 점수인가요?

아닙니다. G0–G7은 release·안전·상태정직성·현재성·기본유용성·증거·모바일 요건을 확인하는 필수
통과조건입니다. 점수가 높아도 하나가 확정 `FAIL`이면 FINAL_Q와 수상대상이 될 수 없습니다.
각 gate의 쉬운 설명은 `05_EVALUATION_PROCESS.md` 4절에 있습니다.

### Q. AI coding tool을 사용할 수 있나요?

예. 사용한 도구·library·SDK와 license를 신고하고, 제출한 code가 어떻게 동작하는지와 언제 실패하는지
(failure boundary)를 직접 설명하고 진단할 수 있어야 합니다.
